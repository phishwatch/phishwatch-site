PhishWatch

Privacy Policy

Last updated: October 22, 2026. Draft for counsel review. Text marked [for counsel], [pending], [pending release] or [VERIFY] is not final.

Short version: PhishWatch checks pages in your browser first. When a local check finds a reason to look closer, the extension sends the address of the link or page to our server, with the names of the warning signs it found and a few short details about them. For a link, the extension sends the full address without the part after # and without any password written into it. A full address can contain personal data, such as an email address in its query string. Our server uses the address for the check and does not store it. For the page you are on, the extension sends the address without the values in its query string. PhishWatch does not send page content or anything you type into a page. If you use PhishWatch without a key from an IT service provider, we do not store your checks [pending release]. If your organisation uses PhishWatch through an IT service provider (MSP), our server stores two records of each check: the domain with the result, which we delete after 30 days, and an event with the domain, the signal names and the result details, which we delete after 90 days. The extension sends further telemetry only if you or your organisation turn it on; we delete it after 90 days.

1. Who we are

PhishWatch is operated by Deborshi Seal, Berlin, Germany. For privacy questions, contact privacy@phishwatch.io. PhishWatch is registered as a sole trader operating under German law [for counsel: update on incorporation].

2. What PhishWatch does

PhishWatch is a Chrome browser extension that detects browser-native phishing attacks at the moment of user interaction, intercepting at the click, redirect, and fake login stages, before credentials are exposed. All detection runs locally in your browser first. Cloud-based analysis is only triggered when local signals indicate risk.

3. Data we transmit during cloud analysis

When a local check finds a reason to look closer, the extension sends the following data to our backend (api.phishwatch.io) for a risk assessment:

Data elementWhat it is
Address being checkedFor a link you clicked: the full link address, including its path and query string. The extension removes the part after # and any user name or password written into the address, and does not shorten it. Our server rejects an address longer than 2048 characters, and the extension then lets you continue. The query string can contain personal data, for example an email address. For a page check: the page's origin and path plus the names of its query parameters, without their values. Example: https://suspicious-login.com/verify?session=. Where we store anything (Section 5), we store only the domain (https://suspicious-login.com), never the path or query.
Download addresses in commandsIf a command that was copied to your clipboard, or that a page tried to put there, downloads a file, the extension sends the download address as its domain, path and query parameter names. It sends no other clipboard text.
Signal IDsIdentifiers of phishing signals that fired locally, e.g. cross_origin_credential_post. They contain no page text.
Signal detailsThe severity of each signal and short details about it. Examples are true/false flags such as has_lure_context: true, counts, hostnames, the origin a sign-in form sends to, the origin and path of a form's target address (never its query), and the path of an address cut to 64 characters. The extension sends only fields on a fixed list. It cuts each text value to 64 characters (280 for two fields that hold an origin) and each structured value to 512 characters.
Extension versionVersion string of your installed PhishWatch extension, e.g. 3.0
Request detailsA random ID for each request. If your organisation set up PhishWatch through an MSP, the request also carries the MSP's key, which tells our server which organisation the check belongs to.
Session IDA random ID that the extension creates for each page you open and keeps in memory only. It is not linked to your identity.
TimestampWhen the event occurred (ISO 8601 format).

To see where a link leads, our server may open the address itself and follow up to 8 redirects. Before it does, it removes query parameters that look like secret tokens (for example password-reset or sign-in codes). The website at that address therefore receives a request from our server. Our server also looks up when the domain was registered (Section 7), using the domain name only.

Fixed list of fields: The extension's background script removes every field that is not on its fixed list before it sends anything. It drops unknown fields.

Tokens inside a link's addressNever storedIf a link you click carries a token in its query string, the extension sends the token with the address for scoring (Section 3). Our server holds it in memory only, and removes token-like parameters before it opens the address.
Browsing historyNeverPhishWatch reacts to clicks and pages that raise a local warning sign. It does not monitor your browsing in the background.

IP address (end user)Never storedWe do not write the IP address of extension users to disk or to our database. Our server holds it in memory for rate limiting until the server restarts or the entry expires [pending release]. Our hosting provider (Render) and its network provider (Cloudflare) handle IP addresses in transit to deliver requests. Our web server's access log records the address of each request today; we are removing the address from that log [pending release]. For MSP server-to-server API calls, we record the IP address of the most recent API key authentication to detect a compromised key (see Section 5).

5. Scan records and telemetry

Checks without an MSP key. If you installed PhishWatch yourself, or use the public demo, we do not store your checks in our database [pending release].

Records for MSP customers. For every check made with an MSP's key, our server stores two records when storage is turned on. You do not need to opt in for these records. The first is a scan record: the domain (scheme and host only), the risk result and score, the names of up to three signals that fired, the MSP's organisation ID and a timestamp. A second, related record, which we use to compare scoring versions, holds the domain, the signal names and the scores. We delete both after 30 days. The second is an event record: the domain, the signal names with their severity and weight, the risk result, the summary shown to you, why the extension started the check, the session ID and the MSP's organisation ID. We delete it after 90 days. None of these records contains a path, query, page content or user identifier. Legal basis: [for counsel] (draft: the MSP's instructions as controller, or legitimate interest under GDPR Art. 6(1)(f)).

Telemetry from the extension. The extension can also report its own events. This telemetry is off by default. You turn it on in the extension popup, or your organisation turns it on through managed browser policy. Our server accepts these events only with an MSP's key.

With telemetry turned on, the extension may send these events:

EventWhen the extension sends it
ScanEach time PhishWatch assesses an address
WarningWhen the extension shows you a warning
DecisionWhen you act on a warning (proceed, cancel, or report a false positive)
Session incidentWhen a redirect chain and a cross-origin sign-in form appear in the same browser tab session, which is a correlated attack sequence
Credential interactionWhen a login form on the page would submit credentials to a different domain than the one shown in your browser
Daily check countsAbout once a day: how many checks the extension made and how many failed, for example through timeouts or network errors. The report contains counts only, with no domain, address, session ID or device identifier.

Telemetry events carry the domain, never the full URL, together with the signal and decision fields listed above, the page's referrer origin and your browser language. Our server reduces any address to its domain before it stores the event. The events contain no credentials, page content or user identifiers. If you report a false positive, our server emails PhishWatch the domain, the risk result, the signal names, the session ID and the MSP's organisation ID through Gmail (Section 7).

Storage and retention

We store scan records, event records and telemetry in a Postgres database that Render Services, Inc. hosts in its Frankfurt, Germany region. We delete scan records after 30 days, and event records, telemetry and daily check counts after 90 days. Render, Cloudflare and Google are US companies; how this policy describes transfers under the GDPR is [for counsel].

Server logs. Our server logs never contain a full address, path or query string. No log line about a check names its domain [pending release]. A few log lines about MSP telemetry name the domain: one records that a false-positive email was sent, and others record telemetry that arrived while storage was off or over its rate limit. Our web server also logs each request's endpoint (not the checked address) and the connecting IP address; we are removing the IP address and query string from that log [pending release]. Our hosting provider keeps logs for its log retention period [VERIFY: Render log retention].

MSP account security monitoring

For MSP accounts, we record the IP address of the most recent server-to-server request to our API that authenticates with the MSP's key. Requests from the browser extension do not count: each extension request with the key clears the stored address. We use this address only to detect whether someone has stolen a key and uses it from an unexpected place. It belongs to the MSP's or its integrator's server, not to a browser extension user. Each new server-to-server request replaces it, and we delete it with the MSP's account data. Lawful basis: legitimate interest (GDPR Art. 6(1)(f)), because key-compromise detection is a security measure that protects both PhishWatch and the MSP customer [for counsel].

6. Local storage

PhishWatch stores the following data in your browser:

  • "Continue anyway" choices: addresses you chose to open despite a warning, per tab, in session storage that the browser clears when it closes. A local log of these choices keeps the origin only (up to 500 entries).
  • Telemetry preference: your choice of whether to turn on telemetry. Chrome may sync it to your other devices if you are signed in to Chrome.
  • Sign-in behaviour: which origins a sign-in page normally sends data to, so that the extension notices a change.
  • Check counts: running counts of checks and failed checks, with no addresses.
  • Settings and rules: the MSP's key if one is configured, and the signed detection rules.

This data stays on your device, with one exception. If telemetry is on and an MSP's key is configured, the extension sends the check counts to our server about once a day (the daily check counts in Section 5). Without telemetry, the extension resets the counts each day and never sends them.

7. Third-party services

Domain age checking (RDAP/WHOIS): PhishWatch's backend queries publicly available domain registration data to detect recently registered domains. For most domains, it asks rdap.org, a public RDAP service that needs no API key and refers the query to the registry for that domain. For German (.de), Austrian (.at), Swiss (.ch), Croatian (.hr) and Czech (.cz) domains, it also sends a WHOIS query to the national registry. It sends only the domain name, with no session IDs, signal data or user information. These are public infrastructure services, not commercial third parties [for counsel]. If the query fails or returns no data, our server skips this check and you can continue normally.

Render Services, Inc.: Our backend API and database run on Render's managed platform in its Frankfurt, Germany region. Render processes data on our behalf under a data processing agreement [for counsel]. Render encrypts the database at rest (AES-256). For enterprise and compliance details, see our compliance page or ask for our GDPR Article 32 technical measures document.

Cloudflare, Inc.: Render uses Cloudflare's network in front of its servers. Requests from the extension pass through Cloudflare, which handles them in transit, including the address being checked and your IP address.

Google (Gmail): Our server sends email through Gmail. It sends false-positive reports (Section 5), weekly summaries to MSPs (counts only, no domains), and the reason and comment you enter on the page shown after you uninstall PhishWatch.

Your MSP's systems: If your MSP has set up a webhook, our server sends warning and incident events to the address the MSP chose. These events hold the domain, the risk result, the signal names, the session ID, the time and, for incidents, the sites involved.

The website being checked: When our server opens an address to follow its redirects (Section 3), that website receives the request from our server.

No other third-party services receive any data from the PhishWatch extension. Which of these providers act as processors on our behalf is [for counsel].

This website (phishwatch.io)

The website is separate from the extension and is hosted by Netlify, Inc. Requests to it pass through Cloudflare, Inc. Both process visitor IP addresses to deliver pages. If you click "Accept" in the cookie banner, the site also loads Google Analytics (Google) for visit statistics and Leadfeeder (Dealfront) to identify which companies visit. Both set cookies and may process your IP address, and Google may transfer data to the United States. If you click "Decline" or ignore the banner, neither is loaded. You can change your choice by clearing this site's data in your browser. The legal basis is your consent (GDPR Art. 6(1)(a)) [for counsel]. Netlify Forms receives the pilot application form, and we use it only to respond to your application. 8. Chrome permissions

PhishWatch requests the following Chrome permissions:

  • scripting: runs PhishWatch's own bundled detection scripts in pages, for example to notice when a page writes a command to your clipboard. No remote code is ever loaded.
  • storage: stores your "Continue anyway" choices, preferences, check counts and the signed detection rules.
  • alarms: schedules the periodic check for updated detection rules.
  • Access to all websites (http and https): needed so detection runs on whatever page you visit. Pages are analysed locally, and data leaves your browser only as described in Section 3.
  • api.phishwatch.io: sends flagged addresses and signal names to our backend for risk scoring.

PhishWatch does not request: tabs, history, webNavigation, webRequest, cookies, or any other browsing data permissions.

9. Security

PhishWatch is built on Chrome Manifest V3 with a strict permissions model. The extension uses no eval() and loads no remote code: every script ships inside the extension package, and detection rule updates are signed data, not code. All communication with our backend uses HTTPS/TLS 1.2+. All secrets are stored as environment variables and never committed to code or logs.

10. Your rights and controls

Opt out: You can disable telemetry at any time via the extension popup. Detection continues normally without telemetry.

Uninstall: Uninstalling PhishWatch via Chrome's extension manager removes all locally stored data immediately.

Data deletion: To request deletion of any stored records, contact privacy@phishwatch.io. We will action deletion requests within [for counsel: deadline].

Data portability: Because session IDs are random and have no link to your identity, we cannot extract records attributable to a specific individual. We can export or delete all records of your organisation's MSP account on request. We cannot yet delete the records of one person or one device [pending].

Override: PhishWatch uses a fail-open design. All warnings are overridable, and you can always choose "Continue anyway."
