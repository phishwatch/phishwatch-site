PhishWatch

Privacy Policy

Last updated: October 19, 2026. Draft for counsel review: text marked [for counsel] is not final.

Short version: PhishWatch analyses pages in your browser first. When a local check finds a reason to look closer, it sends the address of the link or page to our server, together with the names of the warning signs it found and a few short details about them. For a link, the full address is sent, without the part after # and without any password written into it. For the page you are on, the address is sent without the values in its query string. PhishWatch never sends page content, anything you type or clipboard contents. If you use PhishWatch without a key from an IT service provider, we do not store your checks [pending P1]. If your organisation uses PhishWatch through an IT service provider (MSP), we store the domain of each check, never the full address, in Frankfurt, Germany, for 30 days. Optional telemetry is off unless you or your organisation turn it on; it is deleted after 90 days.

1. Who we are

PhishWatch is operated by Deborshi Seal, Berlin, Germany. For privacy questions, contact privacy@phishwatch.io. PhishWatch is registered as a sole trader operating under German law [for counsel: update on incorporation].

2. What PhishWatch does

PhishWatch is a Chrome browser extension that detects browser-native phishing attacks at the moment of user interaction, intercepting at the click, redirect, and fake login stages, before credentials are exposed. All detection runs locally in your browser first. Cloud-based analysis is only triggered when local signals indicate risk.

3. Data we transmit during cloud analysis

When local analysis detects risk indicators, the following data is sent to our backend (api.phishwatch.io) for risk assessment:

Data elementWhat it is
Address being checkedFor a link you clicked: the full link address, including its path and query string, up to 2048 characters. Before sending, the extension removes the part after # and any user name or password written into the address. For a page check: the page's origin and path plus the names of its query parameters, with their values removed. Example: https://suspicious-login.com/verify?session=. Where we store anything (Section 5), we store only the domain (https://suspicious-login.com), never the path or query.
Signal IDsIdentifiers of phishing signals that fired locally, e.g. cross_origin_credential_post. No signal content, no page text.
Signal metadataSeverity levels and short details about each signal, for example true/false flags such as has_lure_context: true, counts, hostnames, the origin a sign-in form sends to, the origin and path of a form's target address (never its query), or the path of an address cut to 64 characters. Only fields on an allowlist are sent, and each text value is cut to 64 characters (280 for two fields that hold an origin).
Extension versionVersion string of your installed PhishWatch extension, e.g. 3.0
Request detailsA random ID for each request. If your organisation set up PhishWatch through an MSP, the MSP's key, which tells our server which organisation the check belongs to.
Session IDA random ID created for each page you open, held in memory only. Not linked to your identity.
TimestampWhen the event occurred (ISO 8601 format).

To see where a link leads, our server may open the address itself and follow up to 8 redirects. Before it does, it removes query parameters that look like secret tokens (for example password-reset or sign-in codes). The website at that address therefore receives a request from our server. Our server also looks up when the domain was registered (Section 7), using the domain name only.

Allowlist-based sanitisation: Transmission is controlled by sanitizeClientSignals() in the extension's background script. Any field not explicitly on the allowlist is stripped before transmission. Unknown fields fail closed and are never sent.

5. Scan records and opt-in telemetry

Checks without an MSP key. If you installed PhishWatch yourself, or use the public demo, your checks are not stored in our database [pending P1].

Scan records for MSP customers. For checks made with an MSP's key, we keep a short record so the MSP can see what happened and we can operate and tune detection: the domain (scheme and host only), the risk result and score, the names of up to three signals that fired, the MSP's organisation ID and a timestamp. A second record for comparing scoring versions holds the domain, the signal names and the scores. These records contain no path, query, page content or user identifier, and they are deleted automatically after 30 days. Legal basis: [for counsel] (draft: the MSP's instructions as controller, or legitimate interest under GDPR Art. 6(1)(f)).

Telemetry. PhishWatch also includes an optional telemetry system that reports detection events from the extension. Telemetry is accepted only with an MSP's key. It is disabled by default. You must opt in via the extension popup, or your organisation enables it through managed browser policy, before any of these events are sent.

When telemetry opt-in is enabled, the following event types may be recorded:

Event typeWhen it fires
scanEach time a URL is assessed by PhishWatch
warningWhen an overlay warning is shown to you
decisionWhen you act on a warning (proceed, cancel, or report false positive)
session_incidentWhen a redirect chain and a cross-origin credential form are detected in the same browser tab session, which is a correlated attack sequence
credential_interactionWhen a login form on the page would submit credentials to a different domain than the one shown in your browser
scan_failure_summaryAbout once a day: how many checks the extension made and how many failed (for example timeouts or network errors), as counts only. It contains no domain, address, session ID or device identifier.

Telemetry events carry the domain, never the full URL, together with the signal and decision fields listed above, the page's referrer origin and your browser language. Our servers reduce any address to its domain before storage. No credentials, page content or user identifiers are included. If you report a false positive, an email with the domain, the risk result, the signal names, the session ID and the MSP's organisation ID is sent to PhishWatch through Gmail (Section 7).

Telemetry storage and retention

Scan records and telemetry events are stored on a Postgres database hosted by Render Services, Inc. in its Frankfurt, Germany region. Scan records are deleted after 30 days, and telemetry events and daily check counts after 90 days. Render, Cloudflare and Google are US companies; how this is described under the GDPR transfer rules is [for counsel].

Server logs. Our server logs never contain a full address, path or query string. For checks made with an MSP's key, a log line records the domain, the risk result and the signal names. For checks without a key, no log line records the domain [pending #255]. Our web server also logs each request's endpoint (not the checked address) and the connecting IP address. Logs are kept for our hosting provider's log retention period [VERIFY: Render log retention].

MSP account security monitoring

For MSP administrator accounts, we record the IP address of the most recent successful API key authentication request made directly to our API (not requests from the browser extension). This is used exclusively for security monitoring, specifically for detecting whether a tenant API key has been compromised and is being used from an unexpected location. This IP address belongs to the MSP administrator making the API request, not to any browser extension end user. Each new request of this kind replaces the stored address, and it is deleted with the MSP's account data. Lawful basis: legitimate interest (GDPR Art. 6(1)(f)), because key-compromise detection is a security measure that protects both PhishWatch and the MSP customer [for counsel].

6. Local storage

PhishWatch stores the following data in your browser:

  • "Continue anyway" choices: addresses you chose to open despite a warning, per tab, in session storage that the browser clears when it closes. A local log of these choices keeps the origin only (up to 500 entries).
  • Telemetry preference: your choice of whether to enable telemetry, in chrome.storage.sync, which your browser may sync to your other devices if you are signed in to it.
  • Sign-in behaviour: which origins a sign-in page normally sends data to, so a change can be noticed.
  • Check counts: the running counts of checks and failed checks (pw_scan_failure_counts), counts only.
  • Settings and rules: the MSP's key if one is configured, and the signed detection rules.

This data stays on your device, with one exception: if telemetry is turned on and an MSP's key is configured, the check counts are sent to our servers about once a day as the scan_failure_summary event (Section 5). Without telemetry, the counts are reset each day and never sent.

7. Third-party services

Domain age checking (RDAP/WHOIS): PhishWatch's backend queries publicly available domain registration data to detect recently registered domains. For most domains, this uses RDAP (Registration Data Access Protocol), a public ICANN-maintained service requiring no API key. For German (.de), Austrian (.at), and Swiss (.ch) domains, a direct WHOIS query is sent to the relevant national registry (DENIC, nic.at, or SWITCH). Only the domain name is sent, with no session IDs, signal data or user information. These are public infrastructure services, not commercial third parties. If the query fails or returns no data, this check is skipped and navigation proceeds normally.

Render Services, Inc.: Our backend API and database are hosted on Render's managed platform in Frankfurt, Germany (EU). Render processes data on our behalf under a data processing agreement. The database is encrypted at rest (AES-256). For enterprise and compliance details, see our compliance page or ask for our GDPR Article 32 technical measures document.

Cloudflare, Inc.: Render uses Cloudflare's network in front of its servers. Requests from the extension pass through Cloudflare, which handles them in transit, including the address being checked and your IP address.

Google (Gmail): our server sends email through Gmail: false-positive reports (Section 5), weekly summaries to MSPs (counts only, no domains), and the reason and comment you enter on the page shown after you uninstall PhishWatch.

The website being checked: when our server opens an address to follow its redirects (Section 3), that website receives the request from our server.

No other third-party services receive any data from the PhishWatch extension. Which of these providers are processors acting on our behalf is [for counsel].

This website (phishwatch.io)

8. Chrome permissions

PhishWatch requests the following Chrome permissions:

  • scripting: runs PhishWatch's own bundled detection scripts in pages, for example to notice when a page writes a command to your clipboard. No remote code is ever loaded.
  • storage: stores your local allowlist, preferences and the signed detection rules.
  • alarms: schedules the periodic check for updated detection rules.
  • Access to all websites (http and https): needed so detection runs on whatever page you visit. Pages are analysed locally, and data leaves your browser only as described in Section 3.
  • api.phishwatch.io: sends flagged addresses and signal names to our backend for risk scoring.

PhishWatch does not request: tabs, history, webNavigation, webRequest, cookies, or any other browsing data permissions.

9. Security

PhishWatch is built on Chrome Manifest V3 with a strict permissions model. The extension uses no eval() and loads no remote code: every script ships inside the extension package, and detection rule updates are signed data, not code. All communication with our backend uses HTTPS/TLS 1.2+. All secrets are stored as environment variables and never committed to code or logs.

10. Your rights and controls

Opt out: You can disable telemetry at any time via the extension popup. Detection continues normally without telemetry.

Uninstall: Uninstalling PhishWatch via Chrome's extension manager removes all locally stored data immediately.

Data deletion: To request deletion of any stored records, contact privacy@phishwatch.io. We will action deletion requests within [for counsel: deadline].

Data portability: Because session IDs are random and have no link to your identity, we cannot extract records attributable to a specific individual. We can export or delete all records of your organisation's MSP account on request. Deleting the records of one person or one device is not available yet [pending G7].

Override: PhishWatch uses a fail-open design. All warnings are overridable, and you can always choose "Continue anyway."
